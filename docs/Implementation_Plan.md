# 페이퍼노트(Paper Note) 구현 계획

기능과 동작은 `페이퍼노트(Paper Note) PRD.md`, 화면은 `DESIGN.md`를 따르고, 이 문서는 **어떤 순서로 무엇을 만들고 어떻게 확인할지**만 다룹니다. PRD의 마일스톤 M1~M4는 Phase 1~4에 대응하고, 앞뒤에 준비(Phase 0)와 마무리(Phase 5)를 추가했습니다.

## 1. 진행 원칙

1. **Phase 단위로 진행합니다.** 다음 Phase는 앞 Phase의 완료 기준을 모두 통과한 뒤에 시작합니다.
2. **먼저 확인하고 나중에 만듭니다.** 미확인 가정(CORS, RLS, 인용수 조회)은 Phase 1에서 실제 호출로 확인하고, 결과에 따라 이후 설계를 바꿉니다.
3. **순수 로직은 테스트부터 씁니다.** 중복 합치기, 필터, 정렬, 섹션 분할, JSON 검증, 비용 계산처럼 화면 없이 확인되는 로직은 테스트를 먼저 만들고 통과시킵니다.
4. **화면은 두 테마에서 확인합니다.** Phase 2 이후 새 화면은 모두 academic과 education에서 확인합니다. (education 테마 자체는 Phase 4에서 완성하지만, CSS 변수 구조는 Phase 1에서 잡아 둡니다.)
5. **수정 범위를 지킵니다.** 각 단계는 해당 단계의 기능만 만들고, 다음 Phase의 기능을 미리 넣지 않습니다.
6. 외부 서비스에 쓰기를 하는 작업(Supabase 마이그레이션, 배포 등)은 실행 전에 확인을 받습니다.

## 4. 저장소 구조 (제안)

PRD는 "단일 HTML 배포", DESIGN.md는 "소스는 테마 CSS와 공통 CSS로 나눈다"고 정했습니다. 둘을 함께 만족하도록 **소스는 여러 파일로 나누고, 빌드 스크립트가 `dist/index.html` 하나로 합칩니다.** 빌드는 Node 스크립트 하나로 하며 번들러나 프레임워크는 쓰지 않습니다.

```
PaperNote/
├─ docs/                      PRD, DESIGN.md, 이 문서
├─ design/                    시안 HTML
├─ src/
│  ├─ index.html              뼈대 (테마 초기화 인라인 스크립트 포함)
│  ├─ css/                    tokens-academic, tokens-education, base, components, layout-*
│  └─ js/
│     ├─ adapters/            arxiv, semantic-scholar (공통 형식으로 변환)
│     ├─ search/              merge, filter, sort, cache, queue
│     ├─ ai/                  openrouter, prompts, schema, cost
│     ├─ pdf/                 extract, sections
│     ├─ db/                  supabase 클라이언트, papers, analyses, presets, profiles
│     ├─ ui/                  화면별 렌더링
│     └─ app.js               상태, 화면 전환
├─ tests/                     순수 로직 테스트, 고정 예시 데이터(fixtures)
├─ supabase/migrations/       SQL 마이그레이션 파일
├─ scripts/build.mjs          src → dist/index.html
└─ dist/index.html            배포 결과물
```

- 외부 라이브러리(Supabase JS, pdf.js)는 CDN 스크립트로 불러옵니다. pdf.js는 worker 파일이 따로 필요해 같은 CDN에서 함께 받습니다. 버전은 고정합니다.
- 테스트는 Node 내장 테스트 러너로 순수 로직을 확인하고, 화면은 Playwright로 확인합니다.

## Phase 1. 기반과 위험 검증 (M1)

**목표**: 가장 큰 미확인 가정을 확인하고, 이후 모든 기능이 올라설 DB와 로그인, CSS 구조를 만든다.

### 1-A. CORS와 API 검증 (가장 먼저)

브라우저에서 아래 호출을 직접 해 보고 결과를 `docs/cors-test-results.md`에 기록합니다. 시험용 페이지는 `tests/` 아래에 두고 배포에는 넣지 않습니다.

| # | 호출 | 확인할 것 |
| --- | --- | --- |
| 1.1 | arXiv 검색 (`submittedDate` 범위 포함) | CORS 통과 여부, XML 응답, 날짜 범위 동작 |
| 1.2 | Semantic Scholar 검색 (연 범위, `minCitationCount`) | CORS 통과 여부, 키 없이 호출 한도, 인용수 필드 |
| 1.3 | Semantic Scholar 일괄 조회 (arXiv ID 목록 → 인용수) | CORS 통과 여부, 한 번에 조회 가능한 개수 |
| 1.4 | OpenRouter 호출 (짧은 JSON 출력 요청, 모델 3종) | CORS 통과 여부, JSON 출력이 지켜지는지, 모델별 추론 설정 파라미터 |

**결정 분기**: 막히는 호출이 있으면 그 호출만 Supabase Edge Function으로 중계하고(1.8), 중계가 필요 없으면 1.8을 건너뜁니다. 중계를 만들 때는 OpenRouter 키를 중계 서버에 저장하지 않고 요청 헤더로만 전달하게 합니다. (PRD의 "키는 `openrouter.ai`로 가는 요청에만 사용" 원칙)

**RLS 시험** (SQL과 실제 로그인으로 모두 확인):

- 로그인하지 않은 요청: 모든 `pn_` 테이블 읽기·쓰기 거부
- `pending` 계정: 논문, 분석, 프리셋 읽기·쓰기 거부
- `approved` 계정 A: 자기 행만 읽고 쓰기 가능, 계정 B의 행은 보이지 않음
- 일반 계정이 자기 `status`나 `is_admin`을 고치려는 요청: 거부
- 관리자: 다른 계정의 `status`를 바꿀 수 있음
- Supabase 보안 점검(advisors)에서 RLS 관련 경고 없음

| 2.18 | 임시 로그인과 연결: 로그인 전에는 검색 화면 대신 안내 | 로그아웃 상태에서 데이터 요청이 나가지 않음 |

**완료 기준**
- 프리셋 "통계"로 검색해 두 소스 결과가 합쳐져 나오고, 필터와 정렬이 동작한다.
- 논문을 저장하면 서재용 데이터가 계정별로 쌓이고, 새로고침해도 "저장됨"이 유지된다.
- 순수 로직 테스트가 모두 통과한다.
- academic 테마 스크린샷이 시안 1과 일치한다. 글자 크기 12px 이상.
